## サマリ（3分で読める要約）

### 技術構成の結論

**TypeScript / Next.js（App Router）＋ PostgreSQL（Supabase）＋ Prisma / Vercel** の単一リポジトリ構成。管理画面・API・Webhook・LIFFフォーム・バッチをすべて1つのアプリで持ち、1〜2名で保守できる規模に収める。既存の NAORU ダッシュボードと同じ Vercel 運用のため、インフラ運用の学習コストが増えない。

比較検討した Rails 案・API分離案よりも、**本件の規模（利用者3名・機能数は多いが同時アクセスは少ない）に対して構成が単純**である点を重視した。

### 設計上の重要な3つの判断

1. **LINE友だちと候補者を1つの人物レコードに統合する** — 友だち追加時点で候補者レコードを作成し、フェーズ「LINE登録」から管理する。応募前の見込み候補者も同じ仕組みでタグ付け・検索・配信対象にできる。
2. **採用フェーズ・タグ・フォーム項目をすべて DB のデータとして持つ** — フェーズ追加やアンケート項目の変更を、開発なしで管理画面から行える。集計は表示名ではなく機械可読な `kind` / `funnel_step` を参照するため、名称変更が分析を壊さない。
3. **フェーズ遷移を必ず履歴に残す** — 現在値だけを保持すると要件20の転換率も要件24の入社後分析も算出できなくなるため、`candidate_stage_histories` を Phase 1 の必須要素とした。

### LINE 連携の要点

- Webhook は「署名検証 → 生ログ保存 → 即200 → 非同期処理」の4段構成。LINE の再送・重複に耐え、障害後の再処理もできる。
- **LINEログインチャネル（LIFF）の作成が必要**。リッチメニューの URL は全友だち共通のため、LIFF なしでは「リッチメニュー → 応募フォーム」で回答者を特定できない。
- LINE 公式アカウント側の「あいさつメッセージ」「応答メッセージ」はオフにする（システム側と二重になるため）。
- **既存 LINE アカウントの友だちリストは新アカウントへ移行できない**。誘導配信の計画が必要（`05` A-1）。

### Phase 1 の見通し

準備1週 ＋ 開発7週 ＋ 受け入れ0.5週 ＝ **約8.5週間（開発1名フルタイム相当）**。
要件26の Phase 1 項目をすべて含む。自動配信は Phase 2 だが、テンプレート＋1対1トークを Phase 1 に入れることで、手動運用でも実務が回る状態でリリースする。
