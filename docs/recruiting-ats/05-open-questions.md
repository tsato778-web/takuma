# 05. 確認事項・判断が必要な論点

要件定義書 v1 を読み込んだうえで、**設計を確定させるために回答が必要な項目**を整理した。
A 群は Phase 1 着手前に決めたいもの、B 群は該当スプリント開始までに決めればよいもの、C 群は運用ポリシーとして別途決めるもの。

---

## A. Phase 1 着手前に確定したい（設計に影響する）

| # | 論点 | 背景 | 推奨案 |
| --- | --- | --- | --- |
| A-1 | **既存 LINE アカウントの友だちをどうするか** | LINE の仕様上、公式アカウント間で友だちリストは移行できない。新アカウントを作ると見込み候補者リストはゼロから | 既存アカウントから新アカウントへの誘導配信を実施し、移行期間（例：1か月）は両方を運用。移行者には流入タグ「既存LINE」を自動付与 |
| A-2 | **LIFF（LINEログインチャネル）を使ってよいか** | リッチメニューから応募フォームを開いた際の本人特定に必要（`03` 第1節） | 使う。LINEログインチャネルを追加作成する |
| A-3 | **院長・オーナーはシステムを直接使うか** | 要件25は初期利用者2名だが、要件3では二次面談＝院長、三次面談＝オーナーが担当。評価入力を誰が行うかで権限設計が変わる | Phase 1 は**本部メンバーが代理入力**。院長・オーナーは `users` に「評価者」として登録するがログインはしない（将来の権限追加で対応） |
| A-4 | **八尋さんにアカウントを発行するか** | 要件25は佐藤・若林の2名だが、要件3の配属判断は八尋さんを含む3名 | 3名に発行（全機能利用可）。運用上の不都合はない |
| A-5 | **「年度」の定義** | ダッシュボードの年度フィルタ、「2026年内定済み」の集計基準 | **入社日ベースの年度（4月始まり）** を既定とし、内定日ベースの切替も可能にする。新卒・中途で基準が異なる場合は要指示 |
| A-6 | **資格は複数選択可か** | 柔道整復師と鍼灸師の両方を持つ候補者が想定される | 複数選択可（`candidates.licenses` を配列で保持済み） |
| A-7 | **希望エリアの粒度** | 「エリア」の単位が都道府県か、商圏（例：東京東部）か。複数選択の可否 | エリアマスタを作成し運用側から一覧を提供して頂く。第1〜第2希望まで持てる構造にするかを要指示 |
| A-8 | **LINE を経由しない応募（求人媒体からの直接応募）があるか** | ある場合、候補者の手動登録・CSV インポートが Phase 1 に必要 | 手動登録画面を Phase 1 に含める（LINE 未連携の候補者として登録可能な設計は済んでいる） |
| A-9 | **既存の候補者データを移行するか** | スプレッドシート等で管理中のデータがある場合、CSV インポートが必要 | 対象データの有無と形式をご提供頂き、必要ならインポート機能を受け入れ前に実装 |

## B. 該当スプリントまでに確定したい（機能仕様）

| # | 論点 | 補足 |
| --- | --- | --- |
| B-1 | 面談希望日時（第3希望）から**確定日時を決める運用** | 誰が確定し、誰が候補者へ返信するか。Phase 1 は手動返信＋面談レコード作成を想定。自動調整は Phase 2 |
| B-2 | 二次面談＋店舗見学の**日程調整の担当** | 本部が調整するか、院長が直接候補者と連絡するか。後者の場合、院長への情報連携手段が必要 |
| B-3 | 面談の**キャンセル・リスケ**の扱い | 履歴として残すか、上書きするか（設計上は `status='canceled'` で履歴を残す想定） |
| B-4 | 新卒特有の項目の要否 | 要件5には学校名・卒業予定年度・国家試験の受験状況がない。新卒管理に必要なら項目追加 |
| B-5 | 年齢 vs 生年月日 | 年齢のみだと翌年度に古くなる。生年月日での保持を推奨（表示は年齢） |
| B-6 | 「動画視聴対象」タグの定義 | 未視聴者への再送用か、視聴完了者の識別か。LINE の `videoPlayComplete` で自動判別可能 |
| B-7 | リッチメニューの**タブ切替運用**の有無 | 複数メニューを切り替える場合、リッチメニューエイリアスの登録が必要 |
| B-8 | 東京セミナー（要件18）の管理粒度 | 参加有無フラグのみか、開催日程マスタと紐付けるか |
| B-9 | 通知先 | 新規応募・未対応トーク・配信失敗の通知を Slack／メールのどちらに送るか。Slack ならワークスペースと投稿先チャンネル |
| B-10 | Zoom 録画URL の入力運用 | Phase 1 は手入力。Phase 2 で Zoom API 連携（自動取得）を行うかの意向 |
| B-11 | 一次面談の担当を佐藤さん固定にするか | 将来的に複数名で分担する可能性があるなら、担当者アサイン機能を Phase 1 に含める |

## C. 運用・法務ポリシーとして決めて頂きたい

| # | 論点 | 補足 |
| --- | --- | --- |
| C-1 | **個人情報の利用目的・同意文面** | 応募フォームに掲載する。顔写真・家庭状況・給与といった機微な情報を扱うため必須 |
| C-2 | **データの保存期間と削除ポリシー** | 例：不採用・辞退から2年経過後に個人特定情報を削除（統計データは残す）。削除の自動化が必要かを判断 |
| C-3 | **顔写真の必須／任意** | 必須にすると応募のハードルが上がる。任意（推奨）を提案 |
| C-4 | **給与情報の閲覧制限** | 初期利用者3名のみのため制限不要と判断しているが、将来的に院長・オーナーがログインする場合は要検討 |
| C-5 | **LINE 公式アカウントの料金プラン** | 配信通数の見込み（友だち数 × 月間配信回数）からプランを選定。シナリオ配信開始時にコストが跳ねる |
| C-6 | **アカウント認証（認証済アカウント）の申請** | 検索結果への表示など集客面のメリットがある |
| C-7 | **障害時の連絡経路** | 配信停止・Webhook 停止時に誰が一次対応するか |

## D. 設計側からの提案（要件書に明示されていないが入れておきたいもの）

| # | 提案 | 理由 |
| --- | --- | --- |
| D-1 | **フェーズ滞留日数の可視化** | 「一次面談待ちのまま10日経過」といった停滞を検知できる。要件19の目的（現状把握）を強化する。実装コストは小さい |
| D-2 | **未対応トークの24時間アラート** | LINE 経由の候補者は返信が遅れると離脱しやすい |
| D-3 | **候補者詳細のタイムライン統合表示** | メッセージ・フェーズ変更・タグ付与・評価・紹介を時系列で1本にまとめる。引き継ぎが速くなる |
| D-4 | **一覧からの一括操作** | 複数候補者へのタグ付与・フェーズ変更。運用負荷を大きく下げる |
| D-5 | **監査ログ** | 個人情報を扱うシステムとして最低限必要。後付けは難しいので Phase 1 に含める |
| D-6 | **`LINE_DRY_RUN` モード** | 開発・検証中に実際の候補者へ誤送信する事故を防ぐ |
| D-7 | **面談評価の入力リマインド** | 評価データが揃わないと要件24の入社後分析が成立しない。未入力の面談を一覧表示する |
