# リピスト 基盤設計 — 要件 / MVP / 画面 / 権限 / フロー / 構成

## 1. 要件定義

### 1-1. 目的
「来店した顧客を“次回来店”につなげる」ことに全機能を集約した CRM。一般的なサロン予約システムが「予約を取る」止まりなのに対し、リピストは **再来率（リピート率）の最大化** を中心 KPI に据える。

### 1-2. ターゲット
| 区分 | 内容 |
|---|---|
| 業種 | 美容サロン・脱毛・エステ・小規模美容クリニック |
| 規模 | 1〜数十店舗のチェーン展開を想定 |
| 役割 | オーナー（経営）／店長（店舗管理）／施術者（スタッフ）／受付 |

### 1-3. コア機能要件
| # | 機能 | 概要 |
|---|---|---|
| F1 | 予約管理 | カレンダー予約、スタッフ・席リソース割当、ステータス管理 |
| F2 | カルテ | 施術履歴、写真、肌/体質メモ、同意書、次回提案 |
| F3 | 会計 | 会計伝票、メニュー/物販、複数支払、割引、領収書 |
| F4 | 回数券 | 回数券・サブスク・プリペイドの販売と消化管理 |
| F5 | LINE CRM | LINE 連携、自動リマインド、再来促進ステップ配信、セグメント配信 |
| F6 | KPI分析 | 再来率・LTV・失客・客単価・スタッフ別売上の可視化 |

### 1-4. 非機能要件
- **マルチテナント**: `store_id` による論理分離（将来は法人 = `tenant_id` 階層）
- **権限**: ロールベース（RBAC）＋店舗スコープ
- **可用性**: 表示は高速（一覧 < 1s、予約台帳 1 日表示 < 500ms 目標）
- **監査**: 会計・カルテ・回数券残高の変更は監査ログ必須
- **個人情報保護**: カルテ写真・連絡先はアクセス制御、保管時暗号化
- **拡張性**: 通知チャネル追加に備えイベント駆動

### 1-5. スコープ外（初期）
POS レジ連動ハード、給与計算、在庫発注管理、多言語。

## 2. MVP定義

**MVP の目的**: 1〜数店舗で「予約 → 来店 → カルテ → 会計 → 再来促進」を一周させ、再来率を計測できる状態。

| フェーズ | 含む | 除く |
|---|---|---|
| **MVP (Phase 1)** | 予約管理 / 顧客台帳 / カルテ(テキスト+写真) / 会計(現金・カード) / 回数券(基本) / LINEリマインド / 基本KPI | サブスク課金、複雑セグメント配信、多通貨、LTV予測 |
| Phase 2 | LINEステップ配信・セグメント、回数券サブスク、スタッフ歩合、詳細KPI | — |
| Phase 3 | 法人(tenant)階層、店舗横断分析、API公開、Web予約受付 | — |

**MVP 成功指標**: 1 店舗で実運用に乗り、再来率が日次更新される。

## 4. 権限設計（RBAC × 店舗スコープ）

### 4-1. ロール
| ロール | 主権限 |
|---|---|
| **OWNER** | 全店舗横断、全機能、店舗追加、課金 |
| **MANAGER（店長）** | 自店舗の全機能、マスタ編集、KPI、配信、スタッフ管理 |
| **THERAPIST（施術者）** | 自分の予約/カルテ、会計入力（自担当）、顧客閲覧 |
| **RECEPTIONIST（受付）** | 予約・会計・顧客閲覧、カルテ閲覧（編集不可） |

### 4-2. 強制方針（多層防御）
1. **アプリ層**: 全クエリに `where store_id = :currentStore` を注入（リポジトリ層）
2. **DB層**: PostgreSQL **Row Level Security**（[design/rls-policies.md](./design/rls-policies.md)）
3. **店舗スコープ解決**: `store_memberships` から現在店舗のロールを解決。OWNER は許可店舗集合を持つ

### 4-3. 権限マトリクス（抜粋）
| 操作 | OWNER | MANAGER | THERAPIST | RECEPTIONIST |
|---|:-:|:-:|:-:|:-:|
| 予約作成/編集 | ✓ | ✓ | 自分 | ✓ |
| カルテ編集 | ✓ | ✓ | ✓ | 閲覧 |
| 会計確定 | ✓ | ✓ | 自担当 | ✓ |
| 回数券マスタ | ✓ | ✓ | ✗ | ✗ |
| LINE配信 | ✓ | ✓ | ✗ | ✗ |
| KPI閲覧 | 全店 | 自店 | ✗ | ✗ |
| 店舗設定 | ✓ | 一部 | ✗ | ✗ |

## 5. 予約フロー

### 5-1. 予約取得〜来店
```
[流入] LINE(LIFF) / 受付電話入力 / 管理画面手動
   │
   ▼ メニュー選択 → 所要時間算出 → 空き枠検索（design/availability-search.md）
   ▼ 枠確保 → reservations(status=CONFIRMED) + reservation_items
   ▼ LINE自動: 予約確定メッセージ
   ▼ 来店24h前: リマインド自動配信（reminder_rules: BEFORE_24H）
```

### 5-2. 来店当日〜会計
```
来店 → status=ARRIVED / visits.checkedInAt
   ▼ 施術 → カルテ記入（medical_records, record_photos）
   ▼ 会計 → sales → sale_items(メニュー/物販/回数券消化) → payments(複数可) → CLOSED
   │        └ 回数券使用: customer_tickets.remaining 減算 + ticket_usages
   ▼ status=DONE / visits.checkedOutAt / customer.lastVisitAt・visitCount 更新
   ▼ [再来導線] 次回提案登録 → LINE お礼 → 一定期間未来店で失客前フォロー
```

### 5-3. キャンセル / No-show
- 顧客キャンセル（LINE）→ `CANCELED`、枠開放、キャンセルポリシー判定
- 無断キャンセル → `NO_SHOW`、KPI/顧客リスクに反映

## 6. LINE連携構成

### 6-1. 利用機能
| 機能 | 用途 |
|---|---|
| Messaging API | リマインド・お礼・セグメント配信・自動応答 |
| LIFF | 予約画面・マイページ（回数券残高/履歴）|
| リッチメニュー | 予約 / マイページ / 問い合わせ導線 |
| Webhook | 友だち追加・メッセージ受信 |

### 6-2. 構成
```
顧客 LINE ──┬─ リッチメニュー → LIFF(予約/マイページ) ─→ リピスト API
            └─ メッセージ ──→ LINE Platform ── Webhook ──→ リピスト API
                                                              │
リピスト ──(イベント)→ ジョブキュー → Messaging API(push) ──→ 顧客
            予約確定 / 24hリマインド / お礼 / 失客フォロー / セグメント配信
```
- **店舗ごとに LINE チャネル**（`line_accounts`）。多店舗は店舗単位で別公式アカウント運用が基本
- `line_user_id` ↔ `customer_id` を `line_links` で突合（友だち追加 or LIFF ログイン時）
- 配信は **イベント駆動 + ジョブキュー**（予約時刻起点のスケジュール送信、レート制御）

### 6-3. 自動配信トリガー（reminder_rules）
`予約確定 / 来店24h前 / 当日朝 / 来店お礼(当日) / 7日後フォロー / 30日無来店(失客前) / 誕生日`

## 7. 会計設計（概要）

詳細は [design/accounting.md](./design/accounting.md) / [design/ticket-logic.md](./design/ticket-logic.md)。

- **1来店 = 1 sale（伝票）**、明細は `sale_items`（メニュー / 物販 / 回数券販売 / 回数券消化）
- **複数支払い対応**: `payments` を 1:N（現金 + カード併用など）
- 支払方法: `CASH / CARD / LINE_PAY / TICKET / PREPAID`
- 割引: 伝票単位 + 明細単位。税は内税/外税を店舗設定で
- 回数券: **販売時に売上計上、消化は売上0**（総売上の二重計上回避）
- 会計確定後の編集は監査ログ必須・**赤伝（VOID）方式**

## 8. KPI設計（概要）

詳細は [design/kpi-aggregation.md](./design/kpi-aggregation.md)。

### 中心 KPI（再来特化）
| KPI | 定義 |
|---|---|
| **再来率** | 期間内に2回目以降来店した顧客 / 全来店顧客 |
| **新規→再来転換率** | 新規のうち2回目来店した割合（コホート） |
| **失客率** | 一定期間(30/60日)未来店の顧客割合 |
| LTV | 顧客あたり累計売上 |
| 平均来店間隔 | 来店間隔の平均日数 |
| 客単価 | 売上 / 来店数 |
| 回数券消化率 | 消化回数 / 販売回数 |
| スタッフ別売上/指名率 | 担当別売上・指名比率 |
| No-show率 | 無断キャンセル / 予約数 |

集計は `kpi_daily`（店舗別・日次バッチ）にキャッシュし、ダッシュボードは集計テーブルを参照（高速化）。

## 10. 技術スタック

| レイヤ | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | 型安全・フルスタック共通 |
| フレームワーク | Next.js (App Router) | 管理画面＋LIFF＋API を一体化、既存 Vercel 資産と親和 |
| UI | React + Tailwind / shadcn 系 | 美容クリニック風 UI を高速構築 |
| DB | PostgreSQL | RLS マルチテナント、トランザクション整合、範囲インデックス |
| ORM | Prisma | store_id スコープ、マイグレーション管理 |
| 認証 | NextAuth / 自前 JWT + store_memberships | 多店舗ロール解決 |
| 決済 | Stripe | 既存採用済み、カード/サブスク |
| メッセージ | LINE Messaging API + LIFF | 顧客接点 |
| ジョブ | キュー（Vercel Cron / 外部ワーカー）| リマインド・KPI集計 |
| ホスティング | Vercel（+ マネージド Postgres） | 既存環境踏襲 |

> 既存リポジトリは vanilla HTML + serverless だが、CRM の規模・整合性要件から Next.js + Postgres 移行を推奨。既存ダッシュボードのデザイントークンは UI 資産として流用可能。
